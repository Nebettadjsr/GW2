# GW2 Tool — Current Architecture

## 1. Purpose and authority

This document describes the architecture observed in the source tree as of 2026-09-30. It is a current implementation map, not a normative domain specification or target design. See [Domain Specification](DOMAIN_SPEC.md) for product rules, [Target Architecture](TARGET_ARCHITECTURE.md) for intentional boundaries and future decisions, [Current State](CURRENT_STATE_SPEC.md) for runtime/setup facts, and [Roadmap](ROADMAP.md) for sequencing. The [Crafting Glossary](crafting/GLOSSARY.md) is the canonical mapping of player-facing terms and labels.

## 2. Runtime shape

```text
Browser (Vue 3 / TypeScript / Vite)
       | same-origin HTTP / JSON
       v
Spring Boot web package
       v
Application services ---- repositories ---- PostgreSQL
       |
       +---- GW2 API adapters ----------------+
```

The browser UI is the sole supported product interface. The legacy JavaFX application, its views and its desktop-only presentation code have been removed from the source tree, so no production path or build step starts JavaFX or needs a display (section 9). The backend is Java 25 / Spring Boot 4.1.1, built with Maven. The frontend is in `frontend/` and is built with Vite.

## 3. Source areas and responsibility

- `web.*` contains the Spring Boot entry point, HTTP controllers, request/response DTOs, error mapping, and task coordination.
- `application.*` coordinates Crafting Profit, Discovery, Ectoplasm input support, account/global refresh, price refresh, setup, and bank/material reads.
- `craft.*` contains the persistence-independent crafting model and calculation/resolution logic. It does not import repository types.
- `repo.*` owns PostgreSQL access and persistence-to-domain mapping.
- `sync.*` and `api.*` own synchronization and Guild Wars 2 HTTP adapters.
- `frontend/src/` owns browser screens, HTTP clients, presentation, interaction state, and the explicitly frontend-owned Ectoplasm calculation.
- The default (unnamed) Java package holds no production source. The former JavaFX views, controllers and their presentation helpers lived there and are gone; the shared application, crafting, repository and synchronization code they called is retained and is now reached only through `web.*`.

The primary direction is browser -> HTTP -> application -> domain/repository/API adapters. Domain calculation code remains free of UI, HTTP, SQL/JDBC, and GW2 response-model dependencies. There is no second presentation entry point.

The development workflow is separate from the deployed application. GitHub issues are the work queue. The manually triggered Claude Action selects one ready `auto` issue, works on a dedicated branch, and opens a pull request. Pairing issues are worked locally on the same branch/PR model. The CI workflow runs Maven and Vitest, publishes application coverage, and native Codex review comments on the PR. The review-merge workflow checks the exact PR head, linked auto issue, CI and Codex state before an eligible Claude story can merge; other PRs remain supervised. The retired Python service is preserved at the `pre-github-flow` tag.

## 4. Browser API and workflows

The browser calls same-origin `/api` routes; during development Vite proxies those routes to the Spring Boot server (default port 8080). GW2 credentials and database settings remain backend-side in the current local configuration. The frontend does not contact ArenaNet.

The API exposes Crafting Profit, Crafting Discovery, crafting resolution details, selector options, bank/material reads, item/icon metadata, account Luck, task submission/status, and system status. `GET /api/account/materials` joins the ordered ArenaNet `/v2/materials` catalog with the last synchronized account quantities; every catalog position remains present with quantity zero when unowned. It fails until a material sync has completed, including when no stacks were returned. Ectoplasm Salvage is calculated in the browser from backend-provided inputs; its old backend calculation route is absent. HTTP request/response DTOs are transport models and do not replace domain types.

Crafting Profit's **Refresh data & results** control posts the calculation request and nothing else; the backend admits whatever account and Trading Post refresh its own inputs still need, which covers bank, material storage, account recipe knowledge and character crafting/recipes/inventory and deliberately excludes account Luck. The browser calls no synchronization trigger from this page, so no second account writer can originate here, and the feature does not require a visit to System Status.

`POST /api/crafting/profit` and `POST /api/crafting/profit/resolution` answer from the last successfully published inputs and do not wait for account synchronization or a price fetch (`TARGET_ARCHITECTURE.md` section 9.1, ADR-007). `application.CachedCraftingProfitService` captures the required sources' completion markers and the relevant item set's quote coverage, runs the ordinary calculation when those inputs can produce one, and only then admits the refresh they still need. The response is `200` with the result and a bounded freshness envelope — input generation identity, per-source fresh/stale/missing state, aggregate price coverage, outstanding work with task-status URLs, and bounded retry information — or `202` with that envelope and no rows when no required source has ever synchronized. Expired inputs produce a provisional `200`, never a refusal; a succeeded refresh task alone does not make a result final. The detail route reports whether it still explains the input generation the caller's row came from, and always carries the row recalculated from its own. Input generation identity is derived from the required sources' completion instants, the required item set and a version of the relevant quotes themselves, so a quote refetched inside the reported coverage boundaries or rewritten with new numbers under its existing instant is a different generation even though no coverage aggregate changed.

On the browser side that envelope is consumed by `crafting/useCraftingProfit.ts`, which owns one bounded recovery cycle per context, and presented by `crafting/ProfitRefreshStatus.vue`, which formats supplied states and counts and derives no freshness. The cycle reads the advertised `taskStatusUrl` values through the existing `syncApi.readTaskStatus` and builds no task path of its own; after work completes it resubmits the calculation with the settings currently in effect, because the backend's checks — not a task state — decide whether a result is final. Its clock, waiting and budget timer are injected ports, so the five-minute budget is driven deterministically in tests; the budget is taken once per cycle and covers polling, successive tasks and recalculation, including the calculation an explicit retry asks for. It is enforced both by checks between awaits and by a cancellable timer started with the cycle, so a task-status read or a recalculation that never answers ends the cycle at the deadline instead of animating behind a pending request; the timer is cancelled when the cycle ends first. A monotonic request identifier discards a superseded calculation answer and a cycle counter stops an abandoned cycle at its next checkpoint and discards the answer of a request belonging to it, so a new selection, a settings change, an explicit retry or an expired cycle cannot be overwritten by earlier work, cannot run two cycles at once, and need not assume the backend stopped what it was doing. Every round after the first waits one interval, which bounds the request rate independently of what the backend advertises. The detail request carries the displayed response's `calculationId` as `basedOnCalculationId`, and the detail panel renders the response's own row when the backend reports `RECALCULATED_FOR_CHANGED_INPUTS`, so a row and the tree beside it always come from one generation. `scripts/profit-refresh-browser-smoke.mjs` covers this lifecycle in a real browser against scripted responses, and `scripts/profit-envelope-live-check.mjs` checks the shape those responses imitate against the running backend.

Crafting Discovery takes one character/discipline scope. Its application service uses that character for candidate eligibility and owned inventory, and evaluates one attempt per candidate. The API has no independent inventory-character or max-buy input. Recipe output quantity still affects the revenue from that attempt.

Crafting Profit and Discovery have separate item-ID relevance collectors but share `TradingPostPriceRefreshService`, the same persisted quote repository, freshness rule, GW2 batching path, and price cache. The selected result exposes backend-provided resolution and purchase values; the frontend formats/displays these values and does not reconstruct recursive quantities or acquisition prices. UI label semantics are explained by the linked glossary; domain meaning is specified in `DOMAIN_SPEC.md`.

Crafting Profit and Discovery keep output-name, direct-ingredient and other existing field matching local over the current calculation rows. Indirect matches use a debounced `/api/crafting/ingredient-search` request; it returns only matching recipe IDs and does not trigger a calculation or price refresh. The route queries the shared in-memory `CraftingGraphCache` snapshot, whose item-name catalog was loaded with the graph. It walks the reverse ingredient-to-consumer index, following each reached recipe's output item to all its consumers. The browser intersects those IDs with rows already returned by the current calculation, so search never widens the result scope and never transfers dependency paths or crafting trees. Search is independent of the resolver: a static path can match even when inventory, character eligibility, buying settings or profitability made the resolver buy an intermediate or choose another path.

## 5. Refresh and background work

### Account data

`application.AccountRefreshService` reuses the existing account sync gateway. `refreshCraftingProfitData()` refreshes bank, material storage, account recipes, and character crafting/recipes/inventory, omitting Luck. `refreshAll()` also refreshes Luck and is available through System Status. These unscoped entry points keep their existing behavior, where the first failing source ends the sequence, and their account records and refresh timestamps are single-account/process state; they are not tenant-scoped. The scope-taking `refreshSources(AccountScope, Set)` and `refreshAll(AccountScope)` run each source as its own publication instead, so an independent source still commits when another fails (section 7, *Account-scoped persistence and publication*); no HTTP path calls them yet.

Automatic refresh admission goes through `application.AccountRefreshCoordinator`, which accumulates each caller's required sources into one outstanding set and drains it in a single `ACCOUNT_SYNC` task, one batch at a time. Sources demanded while a narrower batch is in flight are refreshed by the same run, so no second account writer starts. When another entry point already holds the operation key, the coordinator keeps the demand and reports that the named task is not refreshing those sources, rather than adopting it; the next request rechecks and admits what is still required. Admission never establishes freshness — that is read from the completion markers alone — so a task of insufficient scope cannot present its omitted sources as current (`docs/bugs/BUG-2026-001`).

### Trading Post prices

`application.TradingPostPriceRefreshService` accepts the required item IDs from the feature-specific collector. Persisted prices younger than ten minutes are reused. Missing/stale required IDs are fetched in existing batches and upserted; no full-catalog timer runs. The same mechanism serves Profit and Discovery. Status exposes cached/stale counts and newest fetch time where available.

Crafting Profit no longer fetches quotes inside its own request. `application.TradingPostRefreshCoordinator` coalesces concurrent coverage demands into one run under the existing `PRICE_REFRESH_PROFIT` key and gives a demand raised during a run one further pass afterwards, which recomputes the required set and therefore covers ids that became relevant only because account data changed meanwhile. It is coordinated separately from account refresh and introduces no second cache or fetch path. `sync.tp.relevance.CraftingProfitItemCollector` now owns one relevance definition shared by the refresh selection and the coverage report the feature reports freshness from.

### Global game data and crafting graph

`GlobalDataRefreshScheduler` checks global data with a configurable fixed delay. The current defaults are six hours and a one-minute initial delay (`GW2_GLOBAL_REFRESH_INTERVAL_MS`, `GW2_GLOBAL_REFRESH_INITIAL_DELAY_MS`, in `src/main/resources/application.properties`). It submits the same `GlobalDataRefreshService` operation used by the System Status manual action through the in-process `BackgroundTaskService`.

Recipe and TP-tradeable ID lists are fetched before expensive detail data. Unchanged recipe IDs return without recipe detail downloads. Changed recipes are synchronized, including ingredient replacement and removed-ID cleanup; the recipe sync reports a change only after its work succeeds. The Spring application shares one `CraftingGraphCache` instance among both crafting calculation factories, ingredient search and global refresh. `load()` deserializes/builds one immutable in-memory graph snapshot; `rebuild()` loads the recipe catalog and referenced item names, writes the cache file through a temporary file and atomic replacement, then publishes the new snapshot. After changed recipe sync succeeds, global refresh invalidates the shared snapshot and rebuilds it. Readers already holding the old immutable graph finish safely; later readers wait for the complete rebuild and cannot observe a partial graph. A failed rebuild leaves the cache invalidated rather than serving stale recipe relationships. A TP-tradeable list change alone does not trigger a graph rebuild. If the cache is absent, `load()` generates the baseline on first use. Manual graph rebuild is not offered on the current System Status page.

The scheduler catches task failures through the shared task boundary, records the latest global failure in process-local status, and can run again on a later interval. Task history, check/change times, and account refresh times are not durable telemetry and reset on restart.

### Coordination limits

`web.task.BackgroundTaskService` prevents overlapping unfinished tasks with the same operation key within one backend process. It does not use a distributed queue, lock, or shared job store. This is appropriate for today's single-backend-instance runtime. If multiple replicas are introduced, global scheduled work and refresh deduplication need shared coordination (for example PostgreSQL leases/advisory locks); that is future work.

## 6. System Status

The browser destination formerly named Synchronization is presented as **System Status**. It is an admin/diagnostic page, not a normal-user maintenance sequence. It shows account refresh scope/time, global check/change/recipe/graph timestamps, shared TP freshness/counts, tracked task status, and the last global failure where available. Color is paired with text for OK, Problem, Running, and not-run states. Its manual operations are full account refresh and global-data check. Feature flows perform account/price refreshes they need without requiring this page.

## 7. Persistence and current tenancy limit

Account-dependent browser reads and crafting calculations use durable per-source completion markers in `account_sync_state`. A source becomes fresh only when its API fetch and data writes succeed; ordinary reads do not update the marker. The default maximum age is 15 minutes (`gw2.account-data.max-age-ms`, default 900000). Bank/material/Luck screens refresh only their own source; Crafting Discovery refreshes bank, materials, account recipes and characters. For those routes an expired or absent marker admits refresh through the account coordinator and answers `ACCOUNT_DATA_STALE` advertising the task-status URL; the browser waits for completion and retries once. Crafting Profit is not gated that way — see section 4. Static game metadata, Trading Post data and crafting graph invalidation remain on their separate policies.

Each account source writes its rows and its completion marker in one transaction, so a published generation is visible whole or not at all and a failed refresh leaves the previous generation and its marker readable. The character source commits every character payload and its marker together for that reason. A Crafting Profit calculation reads all of its inputs — markers, price coverage, recipes, roster, inventory, quotes and item metadata — through one `REPEATABLE READ` snapshot (`application.ProfitInputSession`), so it cannot pair a part-written refresh with an older marker or mix input generations within one calculation.

PostgreSQL stores shared item/recipe metadata and TP cache data together with one configured account's bank/material, recipe, character, and inventory state. The behavior described in this section is that of an unmigrated database, which is what the retained runtime paths read and write: account data is not consistently keyed by a stable account identity, and only selected newer data such as account Luck has identity-aware persistence. The current local API key is configured by environment. A validated account-access facility now exists and is described below, but it does not yet gate the existing account routes, and the stored rows remain unscoped. This is not multi-user isolation. A database upgraded by the versioned chain in section 8 has the GUID-scoped schema instead, the unscoped paths above are refused on it rather than being served, and the scoped paths that replace them are described under *Account-scoped persistence and publication* below.

The intended future scope is documented in `TARGET_ARCHITECTURE.md`: account state and credentials become account/user scoped, while TP prices, GW2 metadata, and the crafting graph remain shared. Avoid treating the current schema/key model as a desired hosted model. The exact hosted provider is undecided; Cloudflare-related hosting is only a possible option for later evaluation.

### Account-scoped persistence and publication

These paths exist on a migrated database and are what the unscoped paths above are refused in favour of. They take scope as an argument and never resolve one, so nothing below can select an account by itself.

**Scope.** `model.AccountScope` carries exactly one thing, the verified `/v2/account` GUID that is the registry's primary key. It is a dependency-free value record with no no-argument factory, no "current"/"configured"/"last used" accessor and no process-wide holder, so a scoped repository, publication or snapshot requires scope without acquiring an authentication, HTTP or JDBC dependency. A replacement key resolving to the same GUID therefore reuses the existing dataset. Domain types never see it — they receive data the repositories already scoped.

**Scoped reads.** `repo.BankRepository`, `MaterialStorageRepository`, `CharacterRepository`, `InventoryRepository`, `RecipeRepository`, `AccountLuckRepository` and the `sync.tp.relevance` collectors each offer a scope-taking form of their account reads, differing from the unscoped one only in the rows it is given: the owning GUID joins every account table, every join to `characters` carries both halves of the composite `(account_id, character_id)` key, and every scoped entry point calls `ManagedSchema.requireManagedAccountSchema` so it cannot run against the legacy schema. Item metadata, the ordered material catalog, the recipe graph and the Trading Post quote cache stay global and unjoined to any account, so two accounts read the same quotes, positions and icons. Only the *required set* a coverage report measures is account-derived, from that account's recipe knowledge.

**Publication.** `repo.AccountSourcePublication` is the one transaction every account source publishes through. The fetch and its validation complete first and outside it, so no transaction spans a GW2 API call. Inside, the transaction takes a per-account `pg_advisory_xact_lock`, registers the account idempotently, writes the payload, deletes this account's rows the run did not refresh, advances the account/source generation in `account_source_state` and records successful-sync activity — all committed together or rolled back together. Two publications for one account therefore queue instead of interleaving, two publications for different accounts take different keys and neither waits, and a failure leaves the previous rows, generation and completion time exactly as they were. Success always advances the generation, including a successful empty or unchanged payload. `sync.AccountSync` publishes bank, materials, account recipes and Luck this way; `sync.CharacterSync.publishRoster` publishes the roster and every character's crafting, recipe and inventory payload as one source, deleting characters the run did not refresh and cascading their children. A validated empty roster is published like any other empty source: a lost `characters` permission is an HTTP 403 the fetch throws on and a non-array body is rejected by the parser, so an empty `/v2/characters` array means the account owns no characters. Conversely a character the roster named whose detail response cannot be parsed aborts the publication before the transaction opens, because publishing the remainder would delete that character as stale. `application.AccountRefreshService.refreshSources(AccountScope, Set)` runs each requested source as its own publication, so one that succeeds commits even when another fails, and the failures are reported together afterwards rather than being swallowed.

**Freshness and generations.** `repo.AccountSourceStateRepository` owns the `(account_id, source)` markers. No row means *missing* — never "empty" and never inferred from whether the data tables hold rows — so after the reset every source stays missing until a fresh publication. The generation starts at 1 and advances once per successful publication, which is what distinguishes two publications whose payload and completion instant look alike; a timestamp is not a generation identifier. Reads are pure `SELECT`s, so capturing freshness never creates it, and the retired singleton authorities (`account_sync_state` per source, the `account_materials_sync` id-1 row) no longer answer for whichever account synchronized last.

**Scoped snapshots.** `application.ProfitInputSession.open(AccountScope)` opens the same single `REPEATABLE READ` transaction as the unscoped form with the account carried alongside, and issues no DDL because `account_source_state` is Flyway-owned. That account's rows, that account's markers and the shared global inputs are all read from it. The capture records the account and the generation it actually read per source, and `CalculationInputVersions.calculationId()` includes both, so a detail computed for one account can never be reported as explaining another's row, and a later publication cannot be mistaken for the one the calculation saw. The authorized use is recorded before the transaction begins, while the connection is still in autocommit, so the snapshot never becomes a writing transaction holding row locks for the calculation's duration; that one statement registers or reuses the verified account, so a calculation is a recorded visit even for an account that has not published a source yet.

**Activity.** `repo.AccountRegistryRepository` keeps the registry's three `TIMESTAMPTZ` columns. Registration is an `ON CONFLICT DO NOTHING` insert, idempotent for concurrent callers by the primary key itself rather than by a check-then-insert race. Both activity updates are monotonic through `GREATEST`, which ignores NULL arguments: a missing timestamp is filled by the first real event and a late-arriving earlier instant cannot move either column backwards. `last_seen_at` advances on successfully authorized use and `last_successful_sync_at` inside a successful publication; rejected scope and failed proof reach neither. They differ in whether they may establish the identity they describe: `recordAuthorizedUse` registers the verified account in the same statement that advances `last_seen_at`, because a successful authorized read is the one event that can precede any publication — an account that has never synchronized, including every account after a reset, would otherwise have its activity silently discarded. `recordSuccessfulSync` stays a plain `UPDATE`, since the publication transaction has already registered the account. Neither touches `display_name`, `created_at` or the other's column. Missing history stays NULL rather than being fabricated, and activity is never freshness — `account_source_state` remains the only freshness authority. No cleaner exists: removal still requires measured impact and an explicit threshold decision.

**What is still not integrated.** This is the persistence and publication half only. The HTTP boundary does not yet resolve a session into an `AccountScope` and pass it to these paths, so the account routes, task ownership, the browser credential lifecycle and multi-user refresh admission remain the follow-up stories' work, and `gw2.account-access.enforce` stays `false`. Until then a migrated database still answers account requests as unavailable through the refusals in section 8 rather than serving them through the scoped paths above.

### Validated account access

`application.access` owns the access decision, `infra.access` proves credentials upstream, and `web.access` maps the outcomes onto HTTP. The domain is untouched: authorization lives entirely at the HTTP and application boundaries.

**Proof and identity.** `POST /api/session` validates a transient GW2 key against both `/v2/account` and `/v2/tokeninfo` with that same key (`infra.access.Gw2AccountProofAdapter`, parsing shared with the fixture adapter through `Gw2ProofResponses`). Only the `/v2/account` `id` GUID establishes identity; the account name and the key's own id never do. The key's modelled `tokeninfo` permissions, its `urls` restriction and its expiry become the session's effective scope, so a replacement key is proved on its own merits and inherits nothing from a previous one. A response that is not the documented shape fails closed and issues nothing.

**Sessions.** `application.access.AccountSessions` keeps sessions in bounded process memory. The identifier is 256 bits of `SecureRandom` material and is never retained — only its SHA-256 verifier is a key in the store — and the GW2 key is never passed in at all, so a session is not an upstream credential. Expiry is absolute: 15 minutes after successful proof, or the credential's own earlier expiry, computed once and only ever read. Reads and polling cannot extend it, renewal issues a new session rather than lengthening the presented one, and the store evicts the eldest proof past `gw2.account-access.session-capacity`. Eviction, expiry, logout and process restart all require fresh proof.

**Transport contract.** The session identifier travels in a host-only `GW2_SESSION` cookie — `HttpOnly`, `SameSite=Strict`, no `Domain`, no `Max-Age`, and `Secure` for every origin except plain HTTP on a loopback host. Proof, renewal and logout are all state-changing and all validate `Origin` first, including proof; a missing `Origin` is rejected rather than trusted. Proof and renewal return a fresh non-secret `accessContext` bound to that exact session, which the browser echoes in `X-Account-Context` on every account request. Keys are accepted only in `X-GW2-API-Key` on proof, renewal and explicit keyed operations, never in a URL, body or cookie. Every credential-bearing and account response is `no-store`, and no response, log record or exception message carries a key, a session identifier or an account GUID.

**Request context.** `web.access.AccountAccessInterceptor` requires a live session plus a matching access context before any account work and publishes the resolved immutable `AccountContext` as a request attribute (`RequestAccountContext`) rather than thread or process state, so an admitted operation keeps the scope it was admitted with. It is registered at highest precedence and therefore runs ahead of the account freshness interceptor, so a rejected request opens no connection and admits no refresh. A caller-supplied `accountId` is a consistency assertion only: it may agree with the resolved scope and can never select one. Missing, unknown or expired sessions answer `401`; context, account and grant mismatches answer `403`; upstream unavailability and rate limiting answer a retryable `503` with bounded `Retry-After` guidance. The bodies are fixed per status, so no answer reveals whether an account exists, what it contains or how fresh it is.

**Grants and keyed operations.** `AccountOperation` declares, per account source, the grants and upstream endpoints that source consumes, and `AccountContext.permits` is the single check every caller uses. `AccountAccessService.authorizeKeyedOperation` additionally revalidates a caller-supplied key's identity and grants against the live session before any upstream admission. A definitive invalid-credential answer revokes the associated session; a transient upstream failure revokes nothing, so a live lease keeps authorizing cached reads through an outage while proof and renewal correctly fail.

**Integration boundary.** This is the facility, not the migration. `gw2.account-access.enforce` is `false` by default: the existing account routes, task ownership, scoped refresh and the browser credential lifecycle are integrated by their own stories, and nothing here yet hands the resolved scope to the scoped persistence paths of section 7, so nothing here yet makes the application multi-user. Revocation is bounded by the 15-minute lease only — there is no cross-process or durable revocation channel. `gw2.account-access.test-fixtures` replaces the live proof adapter with `infra.access.FixtureAccountProofAdapter` for offline verification of this contract and is never set in a deployment.

## 8. Startup, configuration, and build

`web.Gw2ApiApplication` starts Spring Boot and is the only application entry point; `sync.IconSync.main` remains a standalone maintenance utility. The backend uses `repo.EnvConfig` for local environment and `.env` configuration, and Spring properties expose the HTTP port, global scheduler intervals, account data max age, and the account-access settings described in section 7 (`gw2.account-access.enforce`, `.session-capacity`, `.allowed-origins`, `.test-fixtures`). Schema creation and upgrades are owned by the versioned Flyway chain described below. The system is not containerized or deployed.

### Versioned schema lifecycle and cache reset

`infra.db.SchemaInitializer` is the startup schema gate, and it is the first statement of both retained entry points — `web.Gw2ApiApplication.main` and the standalone `sync.IconSync.main`. It runs before the Spring context is created, so no repository, background task or scheduler can reach the database before the chain is validated or applied, and a failure stops the process: service access resumes only once a valid managed schema is ready.

**The chain.** Flyway's open-source Java engine plus its PostgreSQL module (both version-managed by the Spring Boot BOM) apply versioned SQL from `src/main/resources/db/migration`: `V1__global_reference_and_economy.sql` creates the shared half (items, recipes and ingredients, Trading Post cache, ordered material catalog — none of it account-partitioned) and `V2__account_registry_and_scoped_account_data.sql` the account half. There, `account_registry` is keyed by the verified `/v2/account` GUID, `account_source_state` is the one `(account_id, source)` completion/generation relation, every account-owned table carries a non-null GUID referencing the registry, character children reach `characters` through a composite `(account_id, character_id)` foreign key, and `character_items` states its slot semantics with `UNIQUE NULLS NOT DISTINCT` instead of letting nullable location columns decide them. No credential, credential hash, session or application-user field exists in any of these tables. Applied versions are immutable: a correction is a new version, never an edit, because editing one makes every existing database fail checksum validation at startup.

**The three states.** The gate decides from the database, not from configuration. A schema holding Flyway's `flyway_schema_history` is *managed*: the chain is validated and any pending version applied. An empty schema runs the complete chain. A schema holding tables without that history — the legacy manual schema, or one this build does not recognize — is *unmanaged*. Automatic baselining stays off, so a non-empty schema is never silently declared current; Flyway's destructive `clean` stays disabled; and nothing ever repairs a checksum automatically. A failed migration rolls back that version alone (PostgreSQL transactional DDL), earlier versions stay recorded, a retry resumes from that history, and neither a failed migration nor a checksum mismatch resets anything — both fail startup closed.

**The reset, and resynchronizing afterwards.** Because the database is a disposable cache of GW2 API data (UD-016), an unmanaged schema is not adopted, archived or reconciled, and no row's ownership is inferred. The gate drops every table, view and sequence in that schema — shape-blind, so a legacy schema and a drifted one are treated alike — and then applies the complete chain to the emptied schema. This is the only path by which cached data is dropped, it runs in one transaction, and it happens before any writer or scheduler exists. The operator runbook is therefore just: stop the application, start the current version, and let the gate run; no backup, import manifest, provenance ledger or reconciliation step gates the cutover. Afterwards the live account dataset is empty and `account_source_state` is empty, so every account source is *missing* rather than successfully empty — a validated credential creates or reuses its verified account GUID and each source is refilled by fresh synchronization from the GW2 API under the existing freshness rules. Global data is refilled the same way by the ordinary global refresh. Account creation and activity timestamps start from the reset; missing history stays unknown.

**What a migrated database does not serve yet.** The scoped account repositories and publication now exist (section 7, *Account-scoped persistence and publication*), but no HTTP path yet resolves a session into the `AccountScope` they require, so the retained unscoped paths must still not run against the upgraded account schema. `repo.ManagedSchema` recognizes a managed schema and refuses them with an actionable diagnostic: the `account_sync_state` marker path (which every account read and every account writer passes through), the bank, roster, crafting, owned-inventory, recipe-knowledge and material-storage reads, the legacy Luck write, the unscoped account-materials publication, the Trading Post relevance/coverage selections and `IconSync`'s referenced-item selection. `repo.AccountLuckSchema` and `repo.MaterialStorageSchema` become no-ops there instead, because their objects are Flyway-owned and the global material catalog is shared data rather than account data. On an unmigrated database none of this changes behavior. So a migrated database serves global data and reports account access as unavailable; that is the cutover staying gated, not a defect.

**What it does serve: the split global halves.** Three of those refused paths mixed shared and account data in one statement, so the gate took the global feature down with the account one. Each now exists as two selections over the same definition, and the refused unscoped form is retained only for an unmigrated database. `IconSync.globalReferencedOrUnknownItemIds` reads the shared families — items still missing metadata, the material catalog, recipe outputs and recipe ingredients — while `IconSync.accountReferencedItemIds(con, AccountScope)` reads that account's bank, material and character-inventory references; the icon-metadata refresh asks for the global half on a managed database, so it runs with no credential. `CraftingProfitItemCollector.collectGlobal` and `DiscoveryItemCollector.collectGlobal` replace "recipes this account knows" / "recipes it has not unlocked" with the shared crafting graph itself, which is what craftability means with no account in play, and `TpSync.syncTpPricesForProfit`/`ForDiscovery` select through them on a managed database. All variants keep the one shared quote cache, the ten-minute freshness filter and the required-ID-only batching, so a quote any of them refreshes is reused by the others rather than refetched per account, and no variant walks the Trading Post catalog. Only the *required set* differs between them. The remaining unscoped account read a global workflow passes through, `BankRepository.loadBankSlots()`, returns no rows on a managed database instead of refusing: an absent scope contributes no account row, which is what keeps the item-icon read path usable — it is never a claim that the bank is empty or that a source synchronized, since per-source completion stays in `account_source_state`.

Run backend tests with `./mvnw test jacoco:report`; frontend coverage uses `npm run test:coverage` under `frontend/`. `TEST_STRATEGY.md` defines the test layers, local prerequisites, browser smoke checks, CI gate, coverage KPI, and performance acceptance procedure. CI collects JaCoCo and Vitest V8 reports and publishes a combined summary plus raw/HTML artifacts; coverage is warning-only below the 90% target.

## 9. Removed JavaFX paths and build remnants

The JavaFX application is gone from the production source tree: the `Gw2App` entry point, the Bank, Materials, Ectoplasm, Crafting Profit and Crafting Discovery views, the two crafting view controllers and their presentation helpers (`CraftingResultPresentation`, `StackQuantityFormatter`), and the JavaFX-only `Styles/dark-scroll.css` stylesheet. The desktop-only controls those views offered — the home-screen first-setup/account/global buttons, per-view auto-refresh timers and the Ectoplasm price refresh — have no replacement and are not a parity requirement; browser flows use the HTTP task APIs and the automated global scheduler described above. No production source imports `javafx.*` or `org.testfx.*`, and `src/main/java` has no classes in the default package.

The desktop test layer is gone too. The 31 QA-owned files that verified the removed views — the 19 default-package `*ViewIT`/`Gw2App*IT` integration tests and presentation unit tests, and the 12 TestFX files in `uiverify/` including the `JavaFxUiSupport` and `CraftingUiTestFixtures` fixtures — were retired through the QA test process, so `src/test/java` has no default-package or `uiverify` source left and no test imports `javafx.*` or `org.testfx.*`. The TestFX layer described in `TEST_STRATEGY.md` §32 no longer has a subject.

The application and utility classes the views were the only caller of are gone as well: `application.EctoSalvageService` with its `ecto.EctoSalvageCalculator` (the `ecto` package is now empty and removed), `application.InitialSetupService` with the `sync.IconSyncGateway` seam that existed solely to make it testable, and `util.CoinUtils`, the `"12g 34s 56c"` text parser/formatter the desktop input fields used. No HTTP route mapped to any of them, and nothing in `src/main/java` references them. The Ectoplasm scenario calculation they removed is still a `DOMAIN_SPEC.md` rule, and the browser evaluates it itself; the first-setup sequence has no browser equivalent and is not a parity requirement. The Trading Post seam `api.tp.EctoLivePriceGateway` is retained, keeping `application.ItemReadService` and the browser's item-detail route as its live consumer, as are `sync.AccountRefreshGateway`, `sync.GlobalDataRefreshGateway` and `application.TradingPostPriceRefreshService`, which all keep web consumers.

The desktop icon download is gone with them: `sync.IconSync.syncItemIconsToDisk`, which bulk-downloaded binaries for every item without a local file and recorded the result in `items.icon_path`, and `sync.DesktopIconAdoption`, the legacy `items/{itemId}.png` byte-equality adoption step it was that path's only caller of. Nothing in `src/main/java` now writes `items.icon_path`; the column is still read by `repo.ItemRepository`, `BankRepository` and `MaterialStorageRepository`, which deliberately never put it in a browser response (`STORY-API-009`), so no browser behavior depended on it. Browser icon delivery is unchanged and keeps every shared component: `application.icons.IconDelivery` and `ItemIconUrls` resolve a request through `infra.icons.FilesystemIconStore`, `IconAcquisition`, `HttpIconImageFetcher`, `IconSourcePolicy` and `StoredIcon`, wired in `web.Gw2ApiApplication` to `ICON_CACHE_DIR`, and repair a miss on demand against the same keyed `assets-v1` cache. The icon *metadata* half of `IconSync` is retained in full, including its standalone `main`, and keeps `sync.GlobalDataRefreshGateway` and `application.ItemReadService` as consumers. Legacy `items/{itemId}.png` files left on disk by earlier runs are no longer read by anything.

The JavaFX build and test infrastructure is removed too (`STORY-INFRA-005`): the seven `org.openjfx` dependencies, the `javafx.version`/`javafx.platform` properties, the `org.openjfx:javafx-maven-plugin` plugin, the `main.class` property it read, the `org.testfx:testfx-junit5` test dependency and the CI `-Djavafx.platform=linux` flag. `pom.xml` keeps `spring-boot-maven-plugin` with `web.Gw2ApiApplication` as the only Spring Boot application class (`./mvnw spring-boot:run`); the only other `main` in the tree is the standalone `sync.IconSync.main` utility. The build no longer declares or resolves JavaFX artifacts or a display requirement. `logo.png`, which only the removed home screen loaded, was deleted with it. `src/main/resources/images/` still keeps brand assets (`app-icon.png`, `logo-no-bg.png`, favicons, `site.webmanifest`) that were never referenced from Java at all. They are format-neutral, not desktop UI, so they were left in place.
