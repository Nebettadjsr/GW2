- `STORY-API-003-account-sync-task-endpoint.md` — milestone-04: DONE. `POST /api/sync/account` accepts an account synchronization as a background task (202 with `taskId`/`operation`/`statusUrl` and a `Location` header, no outcome field of any kind) and `GET /api/sync/tasks/{taskId}` reports it; `application.AccountRefreshService` and every JavaFX file unchanged. Asynchronous by UD-007/§23 decision, not by any measured or assumed duration. The controller validates (no request fields accepted — any field is 400 `INVALID_REQUEST`, unreadable JSON 400 `MALFORMED_REQUEST`, both before a task exists) and submits `accountRefreshService::refreshAll` as the task body, so step order, persistence and first-failure short-circuiting stay inside the service and no individual sync step is reachable from a route. New reusable `web.task.BackgroundTaskService` (~150 lines, imports only `java.*`): one virtual thread per task, **at most one unfinished task per operation key** — an overlapping trigger is 409 `SYNC_ALREADY_RUNNING` naming the running task, never queued — in-memory only with the most recent 100 records retained (older terminal ones evicted, unfinished never), nothing persisted, so a restart loses records and shutdown interrupts a task in flight while committed work stays committed. Status distinguishes `PENDING`/`RUNNING`/`SUCCEEDED`/`FAILED` with a known id always 200 (a failed task is a successful lookup) and an unresolvable id 404 `TASK_NOT_FOUND`; failure says "steps that had already completed were not rolled back" and deliberately cannot say *which* steps completed, since the service exposes no step-level progress. Transport-only `web.dto.SyncTaskAccepted/SyncTaskStatusResponse` reusing `ApiErrorResponse` for the failure (`SQLException` → shared `DATA_STORE_UNAVAILABLE`, else `SYNC_FAILED`, exception text logged server-side and asserted absent from responses); a second `SyncApiExceptionHandler` rather than reusing the calculation advice, whose messages describe a crafting calculation. Default suite 234 pass (209 pre-existing + 25 new), including a latch-controlled test proving the trigger returns and the advertised status path answers `RUNNING` while `refreshAll()` is still blocked, exactly-once delegation per accepted task, and zero delegations plus no admitted task for each rejected request. ## Numbering Convention

`STORY-<AREA>-<NUMBER>-short-name.md`. Numbers are sequential **per area**, not global.

Area codes in use: `DOM` (domain-rule stabilization), `TEST` (test infrastructure not tied to one domain rule), `SYNC` (GW2 API / database sync infrastructure), `INFRA` (general technical-debt/infrastructure cleanup not tied to one domain rule or sync flow). New areas start their own counter at 001.

## Archiving

Once a roadmap milestone (`docs/ROADMAP.md` Phase N) is confirmed complete, its DONE stories move from `agent/stories/` into `agent/stories/archive/milestone-NN/` (never deleted) and their entries move here from "Done" to "Archived" under that milestone's own `### Milestone N` heading. This only happens as a deterministic side effect of a confirmed milestone transition during PROJECT PLANNING MODE (see `agent/PLANNER_INSTRUCTIONS.md`), never when an individual story reaches DONE. Phase 0 (`milestone-00`) has already been archived this way; current stories are tagged `milestone-01` (Phase 1).
